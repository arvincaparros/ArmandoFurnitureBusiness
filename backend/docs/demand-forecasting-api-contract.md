# Demand Forecasting API Contract

## 1. Purpose

This document is the authoritative frontend integration contract for the Demand Forecasting backend (Phases A–G, complete). It was generated by direct inspection of the finalized source code, live response payloads (captured by exercising the running application), and the passing test suite — not from the original implementation plan or from assumptions. Where the plan's original expectations diverged from what the code actually does, the code's actual behavior is documented, and the discrepancy is called out explicitly in **§17 Known Issues / Contract Notes**.

## 2. Backend Status

- Implementation: Phases A–G complete.
- Full test suite at the time this document was generated: **130 passed, 0 failed, 0 skipped, 0 regressions** (`pytest -q`).
- Focused suites: `tests/test_forecast.py` — 37 passed. `tests/test_forecast_history.py` — 10 passed. `tests/test_forecast_timeseries.py` — 9 passed.
- Database: Alembic head `c4cebd8094aa`, live database confirmed in sync (`alembic_version` matches, `forecast_results` columns verified against both the migration and the live table).

## 3. Authentication

**Authentication is currently not implemented for these forecasting endpoints.** No `Depends(...)` authentication/authorization dependency, header check, or token validation exists anywhere in `app/routers/forecast.py`. All six endpoints below are open. Frontend integration must not invent an authentication contract (e.g. bearer tokens, API keys, session cookies) for these routes — none exists on the backend today.

## 4. Common Conventions

- **Base path**: all endpoints are mounted under `/api/forecast`.
- **Decimal serialization**: every numeric quantity/confidence field is a Pydantic `Decimal`, and FastAPI serializes `Decimal` to a **JSON string**, never a bare JSON number. Always parse these fields as decimal strings on the frontend (do not assume `parseFloat` precision safety is unnecessary — treat them as strings first).
- **Decimal precision is not fixed across all fields** — it depends on where the value came from. See **§14 Numeric and Decimal Formatting** for the verified, non-obvious precision behavior.
- **No pagination** exists on any endpoint — all list-returning endpoints return their full result set.
- **No authentication, rate limiting, or versioning headers** are present on any response.

## 5. GET /api/forecast

### Purpose
Returns a live, non-persisted forecast for every active product, computed at request time from current sales history. Calling this endpoint does not write anything to the database.

### Request
No path or query parameters. No request body.

### Query Parameters
None.

### Response
`200 OK`, body validated against `ForecastResponse` (`app/schemas/forecast.py`).

```json
{
  "forecast_period": "NEXT_CYCLE",
  "products": [
    {
      "product_id": 2,
      "product_name": "Chair",
      "historical_sales": "12.0000",
      "predicted_demand": "12.0000",
      "trend": "STABLE",
      "confidence_level": "8.33",
      "forecast_status": "LOW_CONFIDENCE"
    }
  ]
}
```

### Response Fields

| Field | Type | Nullable | Notes |
|---|---|---|---|
| `forecast_period` | string | no | **Always the literal string `"NEXT_CYCLE"`** — not a calendar date. See §17. |
| `products` | array | no | One entry per **active** product (`Product.is_active = true`), ordered by `Product.id` ascending. Products with zero sales history are still included. |
| `products[].product_id` | int | no | |
| `products[].product_name` | string | no | |
| `products[].historical_sales` | Decimal string | no | Renamed on the wire from the internal `historical_quantity` — see §15. Never null on this endpoint (falls back to `"0"` for no-history products). |
| `products[].predicted_demand` | Decimal string | no | Renamed on the wire from the internal `forecast_quantity`. Never negative (clamped at 0 in the calculation). |
| `products[].trend` | string | no | One of `INCREASING`, `DECREASING`, `STABLE`, `NO_DATA`. |
| `products[].confidence_level` | Decimal string | no | Always 2 decimal places, e.g. `"8.33"`, `"100.00"`. See §11/§12. |
| `products[].forecast_status` | string | no | One of `READY`, `LOW_CONFIDENCE`, `NO_DATA`. See §11. |

**Confirmed absent from this response**: `historical_quantity`, `forecast_quantity` (verified: these legacy internal key names do not appear in the live JSON; only `historical_sales`/`predicted_demand` do).

### Example

```http
GET /api/forecast
```

Verified live response (captured from the running application, zero-history products):

```json
{
  "forecast_period": "NEXT_CYCLE",
  "products": [
    {
      "product_id": 1,
      "product_name": "Dining Table",
      "historical_sales": "0",
      "predicted_demand": "0",
      "trend": "NO_DATA",
      "confidence_level": "0.00",
      "forecast_status": "NO_DATA"
    }
  ]
}
```

### Errors
None defined. This endpoint has no failure path other than a generic `500` on an unhandled server error (not explicitly modeled — standard FastAPI/Starlette behavior, undocumented payload shape).

## 6. POST /api/forecast/generate

### Purpose
Computes the same forecast as `GET /api/forecast` and additionally **persists** it as a new `ForecastRun` + one `ForecastResult` row per product, making it retrievable later via the history endpoints.

### Request
No path or query parameters.

### Request Body
**None.** This is a bodiless `POST` — no `Content-Type: application/json` payload is read or required. Do not send a request body; it will be ignored.

### Response
`200 OK` — identical schema and field contract to `GET /api/forecast` (`ForecastResponse`). The response reflects the forecast that was just computed and saved.

### Response Fields
Identical to §5.

### Example

```http
POST /api/forecast/generate
```

(no body)

Response shape is identical to §5's example.

### Errors
None defined beyond the generic unhandled-exception case. Note: a database failure during persistence (e.g. a constraint violation) would surface as an unhandled `500`, not a documented `4xx` — there is no explicit `try`/`except` around the persistence call in the router.

## 10. GET /api/forecast/timeseries

### Purpose
Returns a monthly chart-ready series per product: one point per historical month plus exactly one trailing forecast point. Intended to feed a demand chart (historical bars/line + one projected point).

### Request

### Query Parameters
| Parameter | Type | Required | Notes |
|---|---|---|---|
| `product_id` | int | no | If omitted, returns the series for **every active product**. If provided, filters to that single product. |

**No other query parameters exist.** Do not assume date-range filtering, a `months` limit, or a `forecast_horizon` parameter — none is implemented.

### Response
`200 OK`, `ForecastTimeSeriesResponse`.

```json
{
  "products": [
    {
      "product_id": 2,
      "product_name": "Chair",
      "series": [
        {
          "period": "2026-01",
          "historical_sales": "12.0000",
          "predicted_demand": null,
          "is_forecast": false
        },
        {
          "period": "2026-02",
          "historical_sales": null,
          "predicted_demand": "12.0000",
          "is_forecast": true
        }
      ]
    }
  ]
}
```

### Response Fields

| Field | Type | Nullable | Notes |
|---|---|---|---|
| `products` | array | no | One entry per matching active product, ordered by `Product.id` ascending. |
| `products[].product_id` | int | no | |
| `products[].product_name` | string | no | |
| `products[].series` | array | no | Chronologically ordered historical points, followed by **exactly one** forecast point (always last). A zero-history product has a `series` of length 1 (forecast point only). |
| `series[].period` | string, `"YYYY-MM"` | no | See §13 for exactly how this is computed — do not assume it is "next calendar month from today" for every point. |
| `series[].historical_sales` | Decimal string or `null` | yes | Populated on historical points; **always `null` on the forecast point.** |
| `series[].predicted_demand` | Decimal string or `null` | yes | `null` on every historical point; populated only on the forecast point. |
| `series[].is_forecast` | boolean | no | `false` for every historical point, `true` for exactly one point per product (the last one). |

This endpoint does **not** return `trend`, `confidence_level`, or `forecast_status` per point or per product — those exist only on `GET /api/forecast` and the history endpoints. Do not expect them here.

### Example

```http
GET /api/forecast/timeseries
```
Returns all active products' series.

```http
GET /api/forecast/timeseries?product_id=2
```
Returns only product `2`'s series.

### Edge cases (all directly verified against the running code)

| Scenario | Behavior |
|---|---|
| `product_id` omitted | All active products returned, `Product.id` ascending. |
| `product_id` refers to an **unknown** product | `404 {"detail": "Product not found"}` |
| `product_id` refers to an **inactive** product | `404 {"detail": "Product not found"}` (inactive products are excluded from the underlying active-product query, so they're indistinguishable from unknown IDs at the API level) |
| `product_id` is not a valid integer (e.g. `?product_id=abc`) | `422`, FastAPI's standard validation error (see §11) |
| Product has **zero** sales history | `series` has exactly one point: the forecast point, `historical_sales: null`, `predicted_demand: "0"`, `is_forecast: true`. |
| Multiple products requested (no filter) | Each product's series is computed and returned independently; products themselves are ordered by `id`, but there is no cross-product period alignment — each series only contains that product's own relevant months. |

## 11. Forecast Status

Exact values, confirmed in `app/services/forecasting.py::determine_forecast_status()` and exercised by `tests/test_forecast.py`'s boundary tests:

```text
NO_DATA          — the product has zero historical months (n == 0)
LOW_CONFIDENCE    — n >= 1 AND confidence_level <= 50.00
READY             — n >= 1 AND confidence_level  > 50.00
```

Verified boundary (exact quote from source and test names):
- `confidence_level == 50.00` → `LOW_CONFIDENCE` (inclusive on the low side — confirmed by `test_forecast_status_boundary_exactly_50_is_low_confidence` and `test_confidence_long_volatile_history_exactly_50_is_low_confidence`).
- `confidence_level == 50.01` (or any value `> 50.00`) → `READY` (confirmed by `test_forecast_status_just_above_50_is_ready`).

There is no fixed "minimum months" rule for `READY` — the gate is purely the `confidence_level` threshold above, which itself factors in the number of historical months as one of two components (see §12).

## 12. Confidence Level

**Field type**: `Decimal`. **Precision**: exactly 2 decimal places, always (e.g. `"0.00"`, `"8.33"`, `"100.00"`) — confirmed via `.quantize(Decimal("0.01"))` in source and confirmed empirically in every captured live response.

**Nullability**:
- On the **live** endpoints (`/api/forecast`, `/api/forecast/generate`): **never null** — always a computed value, `"0.00"` at minimum.
- On the **history** endpoints: **nullable** — `null` for any persisted run generated before this field existed, or for a run built from a forecast dict that omitted it.

**What it is**: a **deterministic composite score in the range [0.00, 100.00]**, combining two equally-weighted components — a data-volume score (saturating at 6 months of history) and a data-consistency score (based on the coefficient of variation of the monthly demand series). Both components and the final rounding are implemented purely with Python's `Decimal` arithmetic (including `Decimal.sqrt()` for the standard deviation) — confirmed by inspecting `calculate_data_score()`, `calculate_consistency_score()`, and `calculate_confidence_level()` directly; there is no `float()` conversion anywhere in the calculation chain.

**What it explicitly is NOT** — confirmed by the source's own docstring, quoted verbatim:

> "This is NOT a machine-learned or statistical probability - it is a composite score derived purely from the shape of the observed monthly history."

Do not present this value to end users as a prediction probability, an ML confidence score, or a statistical confidence interval. It is a data-quality heuristic only.

## 13. Time-Series Semantics

This section documents the **exact, verified** forecast-period computation in `get_forecast_timeseries()` (`app/services/forecasting.py`) — reported precisely, not simplified.

**For a product with at least one historical month:**
```text
forecast_point.period = the calendar month immediately AFTER
                         that product's own LAST historical month
```
This is computed per-product, from that product's own `get_monthly_historical_demand()` series — it is **not** a single global value shared across all products.

**For a product with zero historical months:**
```text
forecast_point.period = the calendar month immediately AFTER
                         today's date (server clock at request time)
```

**Verified example** (captured live): on a server date of `2026-08-15`, a product with no sales history returns a forecast point with `"period": "2026-09"`.

**Verified example with history**: a product with historical months `2026-01` through `2026-04` returns a forecast point with `"period": "2026-05"` — the month immediately following its own last historical month, regardless of what today's date actually is.

**This is a per-product-anchored design, not a single "next month from today" value applied uniformly.** The frontend must consume the backend-provided `period` string for each point as-is and must **not** attempt to recompute or infer forecast periods independently — different products in the same response can legitimately have different forecast-point periods if their sales histories end in different months.

**Known ambiguity** (see §17): this exact anchoring choice (per-product last-historical-month vs. a single global "next month from today" for every product) was a documented implementation decision made during Phase F, not something explicitly pinned down word-for-word in the original specification. It is internally consistent and fully tested, but flagged here for awareness.

## 14. Numeric and Decimal Formatting

All Decimal fields serialize as **JSON strings**, never bare numbers (verified empirically on every endpoint). Precision, however, **varies by source** — this is a real, verified nuance, not a simplification:

| Field | Endpoint(s) | Type | Nullable | Verified precision behavior |
|---|---|---|---|---|
| `historical_sales` | Live, Time-series | Decimal string | Live: no. Time-series: yes (null on forecast point) | `"0"` (no decimal places) when derived from the in-memory zero-history fallback; `"12.0000"` (4dp) when derived from a real `SalesTransaction.quantity` (a `Numeric(12,4)` column). **Not fixed-width.** |
| `predicted_demand` | Live, Time-series | Decimal string | Live: no. Time-series: yes (null on historical points) | Same variable-precision behavior as `historical_sales` — `"0"` for the zero-history case, `"12.0000"`-style otherwise. |
| `confidence_level` | Live, History | Decimal string | Live: no. History: yes | **Always exactly 2 decimal places** (`.quantize(Decimal("0.01"))`), e.g. `"0.00"`, `"8.33"`, `"100.00"`. |
| `historical_quantity` | History only | Decimal string | no (column is `NOT NULL`) | **Always exactly 4 decimal places**, e.g. `"0.0000"`, `"12.0000"` — because this value is read back from a `Numeric(12,4)` database column, unlike the live endpoint's in-memory equivalent. |
| `forecast_quantity` | History only | Decimal string | no | Same 4-decimal-place behavior as `historical_quantity`, for the same reason. |

**Notable verified discrepancy**: for the identical underlying "zero" value, the **live** endpoint's `historical_sales`/`predicted_demand` render as `"0"`, while the **history** endpoint's `historical_quantity`/`forecast_quantity` for the same product/run render as `"0.0000"`. Both are numerically equal (`Decimal("0") == Decimal("0.0000")`), but the **string representations differ** because the live endpoint's zero comes from an in-memory Python literal while the history endpoint's zero has round-tripped through a `Numeric(12,4)` database column. Frontend code must parse these as decimals for comparison/display formatting and must not do raw string equality checks between the live and history representations of the same value.

## 15. API Contract Differences

### Live Forecast API (`GET /api/forecast`, `POST /api/forecast/generate`)
```text
historical_sales      (renamed from internal historical_quantity — schema-layer alias only)
predicted_demand       (renamed from internal forecast_quantity — schema-layer alias only)
trend
confidence_level       (always present, never null)
forecast_status         (always present, never null)
```
`historical_quantity` and `forecast_quantity` are **confirmed absent** from these two endpoints' JSON output.

### Forecast History API (`GET /api/forecast/history`, `/history/latest`, `/history/{run_id}`)
```text
historical_quantity     (original field name — NOT renamed)
forecast_quantity        (original field name — NOT renamed)
trend
confidence_level         (nullable — null for legacy pre-migration runs)
forecast_status           (nullable — same rule)
```
This is **intentionally different** from the live contract. The rename applied in Phase E was scoped only to `ProductForecast` (the live schema); `ForecastHistoryResult` was never touched.

### Time-Series API (`GET /api/forecast/timeseries`)
```text
period
historical_sales    (uses the live-API vocabulary, nullable — null on the forecast point)
predicted_demand     (uses the live-API vocabulary, nullable — null on historical points)
is_forecast
```
Uses the **live** API's field vocabulary (`historical_sales`/`predicted_demand`), not the history API's (`historical_quantity`/`forecast_quantity`) — confirmed directly from `ForecastTimeSeriesPoint` in `app/schemas/forecast.py`.

**Rule of thumb for frontend developers**: if you're building the forecast table or triggering a new forecast, you're in `historical_sales`/`predicted_demand` territory. If you're reading saved history, you're in `historical_quantity`/`forecast_quantity` territory. If you're building the chart, you're back in `historical_sales`/`predicted_demand` territory (via the time-series endpoint).

## 16. Frontend Integration Guide

```text
Forecast Table
    ↓
GET /api/forecast
    → products[].historical_sales, predicted_demand, trend,
      confidence_level, forecast_status

Generate Forecast (persists a new run)
    ↓
POST /api/forecast/generate
    → same response shape as GET /api/forecast

History List
    ↓
GET /api/forecast/history
    → array of runs, each with products[].historical_quantity,
      forecast_quantity, trend, confidence_level (nullable),
      forecast_status (nullable)

Latest History Run
    ↓
GET /api/forecast/history/latest
    → 404 if nothing has ever been generated

Specific History Run
    ↓
GET /api/forecast/history/{run_id}
    → 404 if the run_id doesn't exist

Chart
    ↓
GET /api/forecast/timeseries?product_id=<id>
    → series[] with historical points (historical_sales set,
      predicted_demand null, is_forecast=false) followed by
      exactly one forecast point (predicted_demand set,
      historical_sales null, is_forecast=true)
```

**Fields that are always present on the live forecast table** (`GET /api/forecast`): `product_id`, `product_name`, `historical_sales`, `predicted_demand`, `trend`, `confidence_level`, `forecast_status` — none of these are nullable on this endpoint.

**Fields that can be null** (history endpoints only, for pre-migration/legacy runs): `confidence_level`, `forecast_status`. The frontend must render a fallback (e.g. "—" or "N/A") for these two fields when consuming history data, since not every historical run has them.

**Status values that exist today**: `READY`, `LOW_CONFIDENCE`, `NO_DATA` — no other values are produced by the backend. Do not build UI branches for any other status string.

**Forecast period is not a real calendar label on the live/history endpoints** — it is the literal string `"NEXT_CYCLE"` everywhere except the time-series endpoint's per-point `period` field, which is a real `"YYYY-MM"` string (see §13). Do not attempt to derive a real date from the live endpoint's `forecast_period`.

**The backend computes forecast values, confidence, status, and forecast periods — the frontend must not recalculate any of these independently.** See §19.

## 17. Known Issues / Contract Notes

These are documented as-is, per instruction, without modifying any backend code:

1. **`forecast_period` is a placeholder literal, not a computed calendar value, on the live and history endpoints.** `GET /api/forecast`, `POST /api/forecast/generate`, and every history endpoint always return the hardcoded string `"NEXT_CYCLE"` — this was never replaced with a real calendar month, unlike the time-series endpoint's per-point `period`, which is a real `"YYYY-MM"` value. This inconsistency (two different "what period is this forecast for" representations within the same feature) is a real, verified characteristic of the current backend, not a documentation gap.

2. **Decimal string precision is not uniform** — see §14 for the full verified breakdown. A frontend comparing a live-endpoint value against a history-endpoint value for what should be "the same number" must compare numerically, not as strings.

3. **Time-series forecast-period anchoring is per-product, not global** — see §13. This is a deliberate, tested implementation choice made during Phase F, carried forward through Phase G's final validation without further change. It was flagged in the Phase F/G reports as resting on an interpretation of an underspecified point in the original specification (the spec's period-computation guidance was written primarily for the live endpoint's single run-wide `forecast_period`, and was never fully pinned down for a per-point, per-product timeline). It is internally consistent and fully covered by tests, but is called out here for explicit awareness before frontend work is built against it.

4. **The forecast history response omits `product_name`.** `GET /api/forecast` includes `product_name` per product; the history endpoints only include `product_id`. A frontend rendering forecast history by product name will need to resolve `product_id` → name itself (e.g. via `GET /api/products`), since the history payload does not provide it.

5. **No authentication exists on any of these six endpoints.** This is stated once here for completeness, in addition to §3.

## 18. Compatibility Notes

- **Live API field rename**: `historical_quantity → historical_sales`, `forecast_quantity → predicted_demand`, applied **only** to `ProductForecast` (the schema behind `GET /api/forecast` and `POST /api/forecast/generate`).
- **Database/ORM column names remain unchanged**: `ForecastResult.historical_quantity` and `ForecastResult.forecast_quantity` are still the actual database column names — verified directly against `app/database/models.py` and the live database. The rename exists **only** at the Pydantic schema boundary (implemented via `validation_alias`, confirmed in `app/schemas/forecast.py`), not in the database, not in `get_forecast()`'s internal dict, and not in `save_forecast_history()`.
- **History API retains its original field names** (`historical_quantity`, `forecast_quantity`) — confirmed unmodified since Phase D.
- **Time-series API uses the live API's vocabulary** (`historical_sales`/`predicted_demand`), not the history API's — confirmed directly from the schema.
- **Legacy history rows may contain `null` for `confidence_level` and `forecast_status`** — confirmed: the Phase D migration added these columns as nullable with no backfill, so any `ForecastRun` generated before that migration (or any run persisted from a forecast dict lacking these keys) will read back as `null` for both fields on the history endpoints.

## 19. Source-of-Truth Rules

### The backend is authoritative for:
- Forecast values (`predicted_demand` / `forecast_quantity`)
- Confidence level
- Forecast status
- Forecast period (both the live `"NEXT_CYCLE"` literal and the time-series endpoint's per-point `"YYYY-MM"` periods)
- Historical demand aggregation (monthly, zero-filled)
- Time-series point ordering

### The frontend must NOT independently:
- Recalculate forecast values from raw sales data
- Recompute confidence scores
- Re-derive forecast status from confidence thresholds
- Compute its own forecast periods (calendar math) — always consume the backend-provided `period` string

The frontend's job is to render what these endpoints return, not to reimplement any part of the calculation chain described in §13/§19.
